# Project MAX V0 — Foundational Concepts

> **Purpose:** This is the canonical learning document for concepts first encountered in Project MAX V0, **The Dirty Bank**. Later version documents should link back here rather than re-explain concepts such as virtual environments, Python packaging, `pyproject.toml`, editable installs, source-system simulation, PostgreSQL basics, manifests, checksums, or the V0 execution model.
>
> This document deliberately mixes **concept and implementation**. A concept is explained where it appears in the actual system, because engineering becomes easier to understand when the abstraction is attached to something that really runs.

---

## 1. What V0 actually is

Project MAX is intended to evolve into a banking Data and AI Factory. V0 does **not** build the factory. It builds the imperfect operational world that the factory will eventually have to ingest, understand, clean, model and operate.

The simplest mental model is:

```text
YOU
 │
 ▼
STREAMLIT / CLI
 │
 ▼
GENERATION CONFIG
 │
 ▼
generate_bank()
 │
 ├── Core banking records
 ├── Merchant reference data
 ├── Device intelligence
 ├── Payment authorizations
 ├── Authentication events
 ├── Fraud / chargeback labels
 ├── Fraud cases
 └── Banking documents
 │
 ▼
OPTIONAL DEFECT INJECTION
 │
 ▼
RAW SOURCE RUN
CSV / JSONL / JSON / PDF / DOCX / TXT / HTML
 │
 ├── Manifest
 ├── Counts
 ├── SHA-256 checksums
 └── Defect ledger when requested

OPTIONALLY:
selected operational records → PostgreSQL
```

The important engineering decision is that a bank does not begin as one clean table or one DataFrame. V0 deliberately produces **independent source systems with different representations and behaviours**.

That is why V0 contains PostgreSQL-shaped core banking data, JSON event feeds, CSV reference feeds, delayed labels, case records and documents rather than one unified dataset.

### What V0 is not

V0 intentionally has no S3 data lake, Kafka, PySpark, Airflow, curated data, machine learning, feature store, FastAPI service, Kubernetes, GPU workload, OCR pipeline, vector database, RAG or agent.

Those are not missing V0 features. They solve later problems.

V0's job is:

> **Create a messy but controlled bank universe that later versions must engineer around.**

# 2. A folder of Python files is not yet a running system

One of the first implementation lessons in V0 is the difference between **source code**, a **Python environment**, and a **running process**.

The repository contains files such as:

```text
src/project_max/generation/orchestrator.py
frontend/streamlit/app.py
src/project_max/cli.py
```

A `.py` file is text. It becomes active only when a Python interpreter executes code that imports or runs it.

For V0, the important entry points are:

```text
Streamlit entry point
frontend/streamlit/app.py

CLI entry point
project_max.cli:main
```

Most other files do not independently "run". They define functions that are imported and called by an entry point.

For example:

```text
app.py
  ↓
create_run()
  ↓
generate_bank()
  ↓
generate_payments()
  ↓
write_jsonl()
```

This is a foundational software concept:

> A system is not a collection of files. It is an **execution graph** in which code calls other code and data moves between components.

# 3. The current working directory: where the shell is standing

When a terminal opens, it is always "standing" somewhere in the filesystem.

In PowerShell, the prompt shows that location:

```text
PS C:\WINDOWS\system32>
```

If a command creates a relative path such as:

```powershell
py -3.13 -m venv .venv
```

`.venv` means:

> Create a folder named `.venv` **relative to the current working directory**.

So if the shell is standing in `C:\WINDOWS\system32`, the environment is created there. If it is standing in the MAX project root, the environment is created inside MAX.

This is why local setup begins with something like:

```powershell
cd "<path-to-MAX>"
pwd
dir
```

`cd` changes the current directory. `pwd` shows the current directory. `dir` shows what is inside it.

This concept appears everywhere in engineering because relative paths, configuration files, build commands and file creation all depend on the process's working directory unless an absolute path is used.

# 4. `Path`: treating filesystem locations as objects

Project MAX uses Python's `pathlib.Path` heavily instead of manually concatenating path strings.

Examples include:

```python
REPOSITORY_ROOT = Path(__file__).resolve().parents[2]
RUNS_ROOT = REPOSITORY_ROOT / ".local-data"
```

The `/` here is overloaded by `Path` to mean "join path components".

Conceptually:

```text
REPOSITORY_ROOT
      +
.local-data
      ↓
<repo>/.local-data
```

Useful `Path` operations used throughout V0 include:

```python
path.exists()
path.mkdir(...)
path.read_text(...)
path.read_bytes()
path.write_text(...)
path.rglob("*")
path.relative_to(root)
path.stat().st_size
```

Using `Path` gives Python a structured representation of filesystem locations and reduces operating-system-specific string handling.

# 5. Python interpreter vs Python project

Installing Python on Windows gives the machine a Python interpreter. That is not the same thing as installing Project MAX.

Conceptually:

```text
WINDOWS
  │
  └── Python 3.13 interpreter
          │
          └── can execute Python code
```

Project MAX adds another layer:

```text
Python interpreter
      ↓
Project-specific environment
      ↓
MAX package + dependencies
      ↓
MAX code executes
```

The repository's package metadata currently declares:

```toml
requires-python = ">=3.11,<3.14"
```

So Python 3.11, 3.12 and 3.13 satisfy the package constraint; Python 3.14 does not.

The README quick-start text is currently narrower and mentions 3.11 or 3.12. The package metadata in `pyproject.toml` is what pip evaluates when installing the project.

# 6. Virtual environments: `.venv`

A virtual environment is an isolated Python environment for a project.

Without one, multiple projects would share the same global Python packages:

```text
Global Python
├── pandas version X
├── streamlit version Y
├── some-library version Z
└── every project fights over the same environment
```

With a virtual environment:

```text
MAX/
└── .venv/
    ├── Python environment
    ├── pip
    ├── pandas
    ├── Streamlit
    ├── Faker
    ├── psycopg
    ├── pytest
    └── Ruff
```

Another project can have a different `.venv` with different package versions.

Creation:

```powershell
py -3.13 -m venv .venv
```

Activation on PowerShell:

```powershell
.\.venv\Scripts\Activate.ps1
```

After activation, the shell usually shows:

```text
(.venv) PS ...>
```

Activation mainly changes environment variables such as `PATH` so that commands like `python` and `pip` resolve to the environment inside `.venv` rather than another Python installation on the machine.

A useful verification is:

```powershell
python --version
```

### PowerShell execution policy

On some Windows installations, PowerShell blocks `Activate.ps1` because script execution is restricted.

A temporary per-process override can be used:

```powershell
Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
```

`-Scope Process` is significant: the change applies to that PowerShell process rather than permanently weakening the machine-wide policy.

The conceptual lesson is larger than this one error:

> Operating systems impose security policies around executable code. Development tooling exists inside those security boundaries rather than outside them.

# 7. `pyproject.toml`: the project's machine-readable contract

`pyproject.toml` is one of the most important files in V0 even though it does not contain business logic.

It tells packaging tools what Project MAX is and what it requires.

Important sections include:

```toml
[project]
name = "project-max"
version = "0.1.0"
requires-python = ">=3.11,<3.14"
```

and direct runtime dependencies:

```toml
dependencies = [
  "Faker>=28,<40",
  "pandas>=2.2,<3",
  "Pillow>=10,<13",
  "psycopg[binary]>=3.2,<4",
  "python-docx>=1.1,<2",
  "PyYAML>=6,<7",
  "reportlab>=4.2,<5",
  "streamlit>=1.50,<2",
]
```

and development dependencies:

```toml
[project.optional-dependencies]
dev = [
  "CairoSVG>=2.7,<3",
  "pytest>=8.3,<10",
  "ruff>=0.8,<1",
]
```

This is configuration, not prose documentation. TOML is a structured configuration format intended to be parsed by tools.

# 8. What `python -m pip install -e ".[dev]"` actually means

This one command exposes several foundational concepts:

```powershell
python -m pip install -e ".[dev]"
```

Break it apart:

### `python`

Use the Python interpreter currently selected by the environment.

### `-m pip`

Ask that Python interpreter to execute the `pip` module.

This is safer than relying on a bare `pip` command because it explicitly ties pip to the current Python interpreter.

### `install`

Install a Python package/project.

### `.`

The current directory. pip finds `pyproject.toml` there and recognizes MAX as a Python project.

### `[dev]`

Install the project's normal dependencies plus the optional group named `dev`.

So V0 receives runtime packages plus development tools such as pytest and Ruff.

### `-e`

Editable install.

The repository says:

```toml
[tool.setuptools.packages.find]
where = ["src"]
```

Therefore the actual Python package lives under:

```text
src/project_max/
```

Editable installation tells Python that this source tree is the installed `project_max` package. Changes to source code are therefore visible without repeatedly copying and reinstalling a packaged snapshot.

# 10. Direct and transitive dependencies

Project MAX directly asks for packages such as Faker, pandas, psycopg and Streamlit.

But installation shows many more packages, such as Altair, NumPy or other libraries that are not explicitly listed in MAX's dependency block.

That is because dependencies can themselves depend on other packages.

```text
PROJECT MAX
│
├── pandas
│   ├── NumPy
│   ├── python-dateutil
│   └── ...
│
├── Streamlit
│   ├── Altair
│   ├── PyArrow
│   └── ...
│
└── pytest
    └── its own dependencies
```

Two terms matter:

**Direct dependency** — MAX explicitly declares it.

**Transitive dependency** — a dependency of something MAX uses.

pip resolves a dependency graph and attempts to choose versions that satisfy all declared constraints.

# 12. Python packages, modules and imports

A Python **module** is usually a `.py` file.

A Python **package** is an importable collection of modules.

For example:

```text
src/project_max/
├── config.py
├── cli.py
├── generation/
│   ├── orchestrator.py
│   ├── payments.py
│   └── ...
└── persistence/
    └── postgres.py
```

Code can then say:

```python
from project_max.generation import generate_bank
```

The import system searches known Python paths for the package.

### The Streamlit frontend import failure

The deployed application originally attempted an absolute import through `frontend...`, but `frontend` was not installed as part of the `src/project_max` package. The deployed runtime therefore raised:

```text
ModuleNotFoundError: No module named 'frontend'
```

The fix was to treat the Streamlit component tree as local application code and use imports such as:

```python
from components.system_flow import render_system_flow
```

and relative imports inside the component package:

```python
from .viewer import render_system_flow
from .styles import SVG_CSS, VIEWER_CSS
```

The foundational lesson is:

> An import works only if Python can resolve the requested module from its import paths/package structure. Local development can accidentally hide packaging assumptions that a clean deployment exposes.

# 13. `python -m`: executing a module

V0 commonly uses commands such as:

```powershell
python -m project_max.cli bootstrap-db
```

This means:

> Use this Python interpreter and execute the importable module `project_max.cli` as a program.

At the bottom of `cli.py`:

```python
if __name__ == "__main__":
    raise SystemExit(main())
```

When the module is executed directly through `-m`, Python assigns it the special name `__main__`, causing `main()` to run.

When the same module is merely imported by another module, that block does not execute.

This is how one Python file can safely contain reusable functions and also act as a command-line program.

# 14. Configuration as data: `GenerationConfig`

V0 centralizes simulation parameters in a dataclass:

```python
@dataclass(frozen=True)
class GenerationConfig:
    seed: int
    customers: int
    transactions: int
    merchants: int
    fraud_rate: float
    as_of: datetime
```

A **dataclass** is a Python feature that reduces boilerplate for classes whose main purpose is holding structured data.

`frozen=True` means instances are intended to be immutable after creation.

Instead of passing six unrelated values everywhere, the system passes one typed object:

```text
GenerationConfig
├── seed
├── customers
├── transactions
├── merchants
├── fraud_rate
└── as_of
```

This makes interfaces clearer and gives one place to validate impossible configurations.

For example, V0 rejects:

- fewer than one customer;
- negative transaction counts;
- fewer than one merchant;
- fraud rates outside 0–1;
- datetimes without timezone information.

This demonstrates a general design principle:

> Validate assumptions at the boundary before invalid data propagates into the rest of the system.

# 15. Type hints: documentation the interpreter can mostly ignore but tools can use

V0 contains annotations such as:

```python
def generate_payments(...) -> list[dict]:
```

and:

```python
rows: list[dict] = []
```

Type hints communicate expected shapes to humans, editors, linters and static-analysis tools.

Examples:

```text
int             integer
float           floating-point number
str             string
Path            pathlib path object
list[dict]      list whose elements are dictionaries
dict[str, list] dictionary with string keys and list values
str | None      either a string or None
```

Python does not automatically enforce all type hints at runtime. V0 still explicitly validates business constraints where correctness matters.

# 16. Reproducibility: randomness that can be replayed

Synthetic banking data must look varied, but engineering tests also need repeatability.

V0 creates a seeded random generator:

```python
rng = random.Random(config.seed)
```

and Faker is seeded separately:

```python
fake.seed_instance(config.seed)
```

A seed turns pseudo-random generation into a reproducible sequence.

Conceptually:

```text
seed 42 + same code + same configuration
                ↓
          same generated sequence
```

This is why the tests can verify that two runs using the same seed produce identical structured source artifacts.

Reproducibility matters for debugging:

> If a failure occurs on synthetic scenario X, an engineer should be able to regenerate scenario X rather than hope random generation produces it again.

# 17. Simulation time and timezones

V0 does not simply call "now" everywhere. `GenerationConfig` carries an `as_of` timestamp.

That creates a controlled simulation clock.

For example:

```text
as_of = 2026-08-20 12:00 UTC
```

Payments are generated relative to that simulation time, customers were created before it, and documents/runs can be understood relative to the same world state.

The validator requires timezone-aware `as_of` values.

Why? Because:

```text
2026-08-20 12:00
```

is ambiguous without knowing whether it means UTC, IST, GMT, etc.

Timezone-aware timestamps reduce ambiguity once data begins crossing systems and regions.

# 18. The orchestrator: one function coordinates the bank

The most important business-execution function in V0 is:

```python
generate_bank(...)
```

in `generation/orchestrator.py`.

It is an **orchestrator**: it does not personally generate every field. It coordinates specialized generators in dependency order.

```text
generate_bank()
 │
 ├── generate_core_banking()
 │
 ├── generate_merchants()
 │
 ├── generate_devices()
 │
 ├── generate_payments()
 │
 ├── generate_authentication_events()
 │
 ├── generate_fraud_labels()
 │
 ├── generate_fraud_cases()
 │
 └── generate_documents()
```

Then it optionally calls:

```text
inject_defects()
```

and, when given a database URL:


A useful analogy:

```text
orchestrator.py = factory manager
individual generators = production stations
common.py = shared tools
output directory = finished shipment
manifest.json = shipping record
```

# 19. Dependency order inside the synthetic bank

The generation order reflects real logical dependencies.

A payment needs:

```text
card
merchant
device
customer identity
```

So those entities must exist before payments are generated.

Authentication events are derived from payment context, so payment records must exist first.

Fraud labels refer to transaction IDs, so transactions must exist first.

Fraud cases refer to fraud labels and transactions, so both must already exist.

The execution graph therefore encodes relationships:

```text
Customers
   ↓
Accounts
   ↓
Cards ───────────┐
                 │
Merchants ───────┼──→ Payments ──→ Authentication
                 │        │
Devices ─────────┘        ↓
                      Fraud labels
                           ↓
                       Fraud cases
```

This is a foundational systems-thinking concept:

> Data generation, transformation and processing pipelines are constrained by dependencies between entities and events.

# 20. Lists and dictionaries: V0's in-memory working representation

Before V0 writes CSV or JSONL files, most generator functions work with ordinary Python objects.

A single customer is represented as a dictionary:

```python
{
    "customer_id": "CUS0000001",
    "full_name": "...",
    "kyc_status": "VERIFIED",
}
```

Many customers become a list of dictionaries:

```python
[
    {...customer 1...},
    {...customer 2...},
    {...customer 3...},
]
```

This shape is used repeatedly because it maps naturally to:

- CSV rows;
- JSON objects;
- JSONL events;
- SQL row inserts;
- pandas DataFrames for display.

A useful mental mapping is:

```text
Python dict       ≈ one record / row / object
Python list[dict] ≈ collection of records
```

# 21. Python reading patterns that appear in V0

V0 uses several compact Python idioms. Understanding the pattern matters more than memorizing the syntax.

## 21.1 List comprehension

Example shape:

```python
selected = [row for row in candidates if condition]
```

Read it as:

> For each `row` in `candidates`, keep it if `condition` is true.

Long form:

```python
selected = []
for row in candidates:
    if condition:
        selected.append(row)
```

## 21.2 Dictionary comprehension

Example pattern:

```python
{row["transaction_id"]: row for row in payments}
```

Read it as:

> Build a dictionary keyed by transaction ID whose values are the corresponding payment records.

This enables fast lookup by transaction ID.

## 21.3 Set comprehension

Tests use patterns like:

```python
{row["customer_id"] for row in payments}
```

A set keeps unique values. This makes it useful for integrity checks such as:

> Are all customer IDs referenced by payments contained within the set of generated customer IDs?

## 21.4 `enumerate`

```python
for index, payment in enumerate(payments, start=1):
```

This iterates through values while also generating a counter.

## 21.5 `setdefault`

Payments group devices by customer using a pattern equivalent to:

```python
devices_by_customer.setdefault(customer_id, []).append(device)
```

Meaning:

> If this customer has no list yet, create an empty one; then append the device.

## 21.6 `lambda`

Payments end with:

```python
rows.sort(key=lambda row: row["timestamp"])
```

The lambda is a small anonymous function meaning:

> When sorting, use each row's `timestamp` as its sort key.

## 21.7 `**` dictionary unpacking

The manifest count construction contains:

```python
{
    **{name: len(rows) for name, rows in core.items()},
    "merchants": len(merchants),
    ...
}
```

`**some_dictionary` expands the key/value pairs of that dictionary into another dictionary.

## 21.8 Keyword-only arguments with `*`

Functions such as:

```python
def generate_bank(output_dir, config, *, include_defects=False, database_url=None):
```

use `*` to require later arguments to be passed by name:

```python
generate_bank(run, config, include_defects=True)
```

rather than an ambiguous positional call.

This improves readability at important behavioural switches.

# 22. Context managers: acquiring and releasing resources safely

V0 repeatedly uses:

```python
with ...:
```

Examples include opening files and database connections.

Conceptually:

```text
enter context
   ↓
resource acquired
   ↓
work happens
   ↓
leave context
   ↓
resource cleaned up even if an error occurs
```

For a file:

```python
with path.open(...) as stream:
    ...
```

For PostgreSQL:

```python
with psycopg.connect(database_url) as connection, connection.cursor() as cursor:
    ...
```

This reduces leaked file handles, unclosed connections and inconsistent transaction handling.

# 23. Source systems: why V0 uses several formats

V0 intentionally avoids pretending every operational system exposes the same interface.

The implemented source world includes:

| Source | Representation in V0 | Why it matters |
|---|---|---|
| Core banking | CSV artifacts + optional PostgreSQL tables | Relational customer/account/card structures |
| Payments | JSONL | Event-oriented transaction feed |
| Authentication | JSONL | Separate event stream linked to transactions |
| Device intelligence | JSONL | Entity snapshots/signals |
| Merchant reference | dated CSV | Batch/reference-file behaviour |
| Fraud/chargebacks | CSV | Delayed labels arriving after transactions |
| Fraud cases | JSONL + PostgreSQL subset | Structured fields plus investigator narrative |
| Policies/procedures | PDF, DOCX, TXT, HTML, image-only PDF | Unstructured enterprise knowledge |

The point is not that these exact formats are universal banking standards. The point is to force later versions to deal with **heterogeneous source contracts**.

# 24. CSV, JSON, JSONL and binary documents

## CSV

CSV represents rows and columns as text.

Good for:

- reference extracts;
- simple tabular exchange;
- human inspection.

Limitations include weak typing and inconsistent conventions between producers.

## JSON

JSON represents structured objects and nested values.

V0 uses ordinary JSON for things such as manifests and defect ledgers.

## JSONL

JSON Lines stores one JSON object per line:

```text
{event 1}
{event 2}
{event 3}
```

V0's `write_jsonl()` serializes each Python dictionary separately and appends a newline.

JSONL is useful for event-like data because records can be processed line by line and individual events remain independently structured.

Important: V0's JSONL files are **simulated event feeds stored as files**. They are not Kafka topics and are not live streaming infrastructure.

## PDF / DOCX / image-only PDF

Documents are different from row-oriented operational data. V0 intentionally creates both machine-readable documents and an image-only PDF with no searchable text layer.

That image-only document exists so a future OCR stage has a genuine reason to exist rather than being added merely as a technology demonstration.

# 25. Cross-system identity: different systems refer to the same real-world thing

V0 preserves identifiers across generated systems.

Payments reference generated:

```text
customer_id
card_token
merchant_id
device_id
transaction_id
```

Authentication events preserve transaction/customer/device relationships.

Fraud labels reference transaction IDs.

Fraud cases reference transactions and customers.

This means the source systems are independent in representation but not random disconnected files.

The unit tests explicitly verify cross-system integrity: payment customer IDs must exist in the customer source, card tokens must exist in cards, merchants and devices must exist, and authentication transaction IDs must match generated payments.

This is a critical data-engineering concept:

> Integration becomes possible because systems share stable keys or mappings that let records refer to the same business entity or event.

# 26. Payment events: event time, emission time and schema version

A payment authorization contains fields including:

```text
transaction_id
amount
currency
timestamp
emitted_at
channel
authentication_method
device_id
authorization_result
schema_version
```

Three concepts matter.

## Event/business time

`timestamp` means when the simulated transaction happened.

## Emission time

`emitted_at` is slightly later and represents when the event was emitted by the source system.

This introduces the distinction:

```text
business event happens
        ↓
source system emits record
        ↓
downstream system eventually processes record
```

Later streaming systems will care deeply about event time versus processing time and late-arriving records.

## Schema version

The payment event carries:

```text
schema_version = 1.0
```

This acknowledges that data contracts evolve. The dirty-data injector later introduces a version `2.0` event with an extra field to simulate schema evolution appearing inside a stream.

# 27. Authentication as a separate source

Authentication is not embedded as if the payment system knew everything.

V0 derives a separate authentication event linked by transaction/customer/device IDs.

For example:

```text
Authentication system
10:14:31  TXN123  OTP_SUCCESS

Payment system
10:14:52  TXN123  INR 12,700  APPROVED
```

Authentication occurs 1–45 seconds before the corresponding payment timestamp in the simulator.

The architectural lesson is:

> A business event is often reconstructed from evidence spread across several systems rather than read from one perfect source.

---

# 28. Delayed labels: truth can arrive after the event

Fraud is not known with certainty at transaction time.

V0 selects some approved transactions as eventually confirmed fraud and generates a later `reported_at` timestamp 2–21 days after the original transaction.

Conceptually:

```text
Day 0
transaction approved
      ↓
Day 5
customer reports fraud
      ↓
truth label becomes available
```

This is one of V0's most important concepts because future ML training must respect what information was actually available at prediction time.

If a model training dataset accidentally attaches a future fraud outcome to an earlier transaction in a way that lets future information leak into features, offline performance can look excellent while production performance collapses.

The V0 tests explicitly verify that fraud labels occur after the transaction and have at least a two-day delay.

# 29. Controlled dirty data: defects as testable requirements

The Dirty Bank is not merely random low-quality data. It deliberately creates **known defects** and records them.

V0 defines 15 defect classes:

| Defect | Fundamental idea |
|---|---|
| `null_values` | required/expected information missing |
| `duplicate_records` | same business record appears more than once |
| `duplicate_transaction_events` | same event emitted twice |
| `inconsistent_country_codes` | producer uses incompatible coding conventions |
| `inconsistent_currencies` | nonstandard currency representation |
| `malformed_timestamps` | time value cannot be parsed correctly |
| `wrong_data_types` | field expected to be numeric becomes text, etc. |
| `late_records` | event arrives much later than its business time |
| `delayed_fraud_labels` | outcome becomes known after the transaction |
| `stale_reference_data` | reference data is old relative to current decisions |
| `unexpected_categories` | undocumented/new categorical value appears |
| `merchant_name_variations` | casing/spacing/suffix changes create entity-matching issues |
| `schema_changes` | new version/field appears unexpectedly |
| `invalid_foreign_keys` | record references an entity that does not exist |
| `duplicated_files` | exact same source file arrives more than once |

The injector writes dirty copies under a `dirty/` directory rather than silently corrupting every clean source artifact.

That distinction gives V0 both:

```text
clean controlled source
+
known corrupted variants
```

This is much more useful for later engineering than an unknown dirty dataset because detection quality can be measured against known ground truth.

---

# 30. The defect ledger: making test data observable

Every intentional defect is recorded with fields such as:

```text
defect_id
defect_type
target
record_id
description
```

The injector verifies that all required defect types were actually created and raises an error if any are missing.

This is an important shift from:

> "The data looks messy."

into:

> "These exact failures were intentionally planted; downstream quality controls can now be tested against them."

The defect ledger is therefore not just documentation. It becomes a future **evaluation oracle** for V1/V2 data-quality logic.

# 31. Immutable runs: do not silently rewrite evidence

`generate_bank()` refuses to overwrite a non-empty run directory.

Why?

Suppose a bug is observed in run A. If the generator later silently rewrites the same folder, the evidence that produced the failure disappears.

V0 instead treats each generated run as a snapshot:

```text
run_A/
run_B/
run_C/
```

This creates a simple prototype form of immutability and reproducibility.

The broader principle is:

> Data used as evidence should not mutate invisibly under the same identity.

# 32. The run manifest: metadata about the generated bank

At the end of generation, V0 writes `manifest.json`.

It records information such as:

```text

version
bank
purpose
seed
as_of
base_currency
counts
document_catalog
database_loaded
file inventory
```

A manifest is **metadata**: data that describes other data.

The files are the source artifacts. The manifest tells us what was generated and how.

That enables questions such as:

- Which seed created this run?
- How many customers/payments/documents were generated?
- Was the PostgreSQL path used?
- Which files belong to the run?
- What size was each file?
- Has a file changed?

# 33. SHA-256 checksums: fingerprints for files

The orchestrator reads every generated file and computes:

```python
hashlib.sha256(data).hexdigest()
```

A cryptographic hash maps arbitrary bytes to a fixed-length fingerprint.

Conceptually:

```text
file bytes
   ↓
SHA-256
   ↓
fixed fingerprint
```

Change even a small portion of the file and the resulting hash will almost certainly change dramatically.

In V0, checksums are useful for **integrity evidence**:

> Is this still the same artifact that was produced when the run manifest was created?

A checksum is not encryption. It does not hide the file contents. It is a compact fingerprint of them.

# 36. The four Streamlit buttons are scenarios, not sequential pipeline stages

The UI exposes four generation actions.

# 38. Local filesystem vs durable storage in Streamlit Cloud

# 40. PostgreSQL: server, database, schema, table and role are different things

Installing PostgreSQL introduces several nested concepts.

A useful hierarchy is:

```text
PostgreSQL server/process
│
├── database: postgres
│
└── database: max_bank
    │
    ├── schema: core_banking
    │   ├── table: customers
    │   ├── table: accounts
    │   ├── table: cards
    │   ├── table: addresses
    │   └── table: customer_status_history
    │
    └── schema: fraud_ops
        └── table: fraud_cases
```

A **server** is the running database service.

A **database** is a logical database managed by that server.

A **schema** is a namespace/grouping inside a database.

A **table** stores rows with defined columns and constraints.

A **role/login** is a PostgreSQL identity that can authenticate and receive permissions.

V0 uses a local role such as `max_app` and database `max_bank` rather than connecting application code as the PostgreSQL superuser.

# 41. pgAdmin is a client, not PostgreSQL itself

pgAdmin is a graphical administration/client tool.

The PostgreSQL server can exist without pgAdmin, and pgAdmin can connect to PostgreSQL servers.

The relationship is:

```text
pgAdmin
   │
   │ SQL / administration requests
   ▼
PostgreSQL server
```

The Query Tool is opened in the context of a particular database connection. That is why selecting only the server node is different from selecting the `postgres` or `max_bank` database and opening its Query Tool.

# 42. DDL: defining database structure

V0 stores PostgreSQL schema creation SQL in:

```text
source-systems/core-banking/sql/001_v0_source_schemas.sql
```

This SQL uses commands such as:

```sql
CREATE SCHEMA ...
CREATE TABLE ...
CREATE INDEX ...
```

These belong to **Data Definition Language (DDL)**: SQL statements that define database structures.

The command:

```powershell
python -m project_max.cli bootstrap-db
```

calls `bootstrap_database()`, which reads the DDL file and executes it through psycopg.

So "bootstrapping" the database means:

```text
connect to max_bank
      ↓
execute schema/table/index definitions
      ↓
empty operational structure now exists
```

Structure creation and data loading are deliberately separate operations.

---

# 43. Primary keys, foreign keys, checks and indexes

The V0 DDL introduces fundamental relational concepts.

## Primary key

Example:

```text
customer_id PRIMARY KEY
```

A primary key uniquely identifies each row in a table.

## Foreign key

Accounts contain a customer reference:

```text
accounts.customer_id
        ↓ references
customers.customer_id
```

The database can reject an account referencing a nonexistent customer.

## `CHECK` constraint

The schema constrains allowed states and temporal relationships, for example restricting status categories or requiring a closing timestamp not to precede an opening timestamp.

Constraints move some correctness enforcement into the database itself.

## Index

Indexes are created on commonly referenced fields such as customer IDs and fraud-case transaction IDs.

A useful first mental model:

> An index is an additional data structure maintained by the database to accelerate certain lookups, at the cost of storage and write overhead.

# 44. psycopg: the Python/PostgreSQL bridge

PostgreSQL is a separate server process. Python cannot manipulate it merely because PostgreSQL is installed.

V0 declares:

```text
psycopg[binary]
```

as a Python dependency.

The path is:

```text
Project MAX Python
       ↓
    psycopg
       ↓
PostgreSQL network connection
       ↓
    max_bank
```

This is a **database driver**: a library that lets application code establish connections, execute SQL and retrieve results.

# 45. Connection strings and environment variables

MAX does not hard-code the database password in source code.

Instead, local setup supplies:

```powershell
$env:MAX_DATABASE_URL="postgresql://max_app:<password>@localhost:5432/max_bank"
```

Break it apart:

```text
postgresql://
max_app          login
<password>       credential
localhost        database server host
5432             network port
max_bank         database name
```

An **environment variable** is configuration supplied to a running process by its environment rather than embedded in code.

The CLI retrieves either an explicitly supplied URL or `MAX_DATABASE_URL`.

This demonstrates a basic security/configuration rule:

> Code may define how to connect, but secrets should be supplied separately from source control.

The repository explicitly avoids creating credentials and avoids writing the actual database URL into the run manifest.

# 46. `localhost` means "this machine"

A subtle but important networking concept:

```text
localhost
```

means the machine/process environment from which the connection is being made.

Locally:

```text
MAX on laptop → localhost:5432 → PostgreSQL on same laptop
```

But from Streamlit Cloud:

```text
Streamlit Cloud → localhost:5432
```

would mean the Streamlit Cloud machine itself, **not the developer's laptop**.

This is why a local PostgreSQL instance is useful as an engineering lab but is not automatically reachable by the public Streamlit deployment.

# 47. Loading data into PostgreSQL

The V0 loader deliberately loads only selected clean operational records:

```text
core_banking/customers.csv
    → core_banking.customers

core_banking/accounts.csv
    → core_banking.accounts

core_banking/cards.csv
    → core_banking.cards

core_banking/addresses.csv
    → core_banking.addresses

core_banking/customer_status_history.csv
    → core_banking.customer_status_history

fraud_cases/fraud_cases.jsonl
    → fraud_ops.fraud_cases
```

It does **not** load every V0 artifact into PostgreSQL.

Payments remain JSONL events. Authentication remains JSONL. Merchant reference remains a file feed. Documents remain files.

This reinforces the architecture:

> PostgreSQL is one operational source-system representation inside the simulated bank, not a universal storage destination for all V0 data.

# 48. Upsert: insert if new, update if already present

The PostgreSQL adapter generates SQL using:

```sql
INSERT ...
ON CONFLICT (...) DO UPDATE ...
```

This is an **upsert**.

Conceptually:

```text
row key does not exist
        ↓
      INSERT

row key already exists
        ↓
      UPDATE
```

Upserts are common when loading repeatable snapshots or synchronizing source records because a rerun does not necessarily need to fail merely because a known key already exists.

The key used for conflict detection depends on the table's identifier, such as `customer_id`, `account_id` or `case_id`.

---

# 49. Database context managers and transactions

V0 uses:

```python
with psycopg.connect(database_url) as connection, connection.cursor() as cursor:
    ...
```

Besides cleaning up the connection, this gives a transaction scope around database work.

A **transaction** groups database operations into a unit of work so that changes can be committed together or rolled back on failure.

This becomes increasingly important as systems perform multi-table changes where partial success could leave inconsistent state.

V0 only introduces the foundation; later versions will encounter more complex transactional and distributed boundaries.

# 54. Unit tests vs integration tests

A **unit test** checks a relatively contained piece of behaviour without requiring a real external server.

For example, V0 can inspect the PostgreSQL DDL text and verify that required table definitions exist without connecting to PostgreSQL.

An **integration test** checks components working together across a real boundary.

V0 includes an opt-in PostgreSQL integration test that:

```text
Python generator
    ↓
psycopg
    ↓
real disposable PostgreSQL database
    ↓
SQL query verifies loaded rows
```

The integration test requires `MAX_TEST_DATABASE_URL` and skips itself if that variable is absent.

It intentionally does **not** fall back to the normal development database, reducing the risk of destructive test behaviour against data someone cares about.

# 55. Assertions: executable claims about expected behaviour

Tests contain statements such as:

```python
assert manifest["version"] == "V0"
```

and set-containment checks verifying referenced identifiers exist in source systems.

An assertion says:

> This condition must be true. If it is false, the test fails.

Tests convert design expectations into executable checks.

# 56. Ruff: static code-quality checking

Linting can catch problems such as:

Linting asks a different question:

Both matter.

# 59. Deployment debugging as dependency-graph debugging

Two cloud deployment failures exposed useful engineering layers.

First, a Python-version mismatch prevented dependency installation. The project declared `<3.14`, while the initial cloud environment was Python 3.14. Selecting Python 3.12 resolved the compatibility boundary.

Second, after dependencies installed successfully, execution failed on an unresolved `frontend` import. That was no longer a dependency-installation problem; it was an import/package-layout problem.

Reading logs layer by layer gives a useful debugging method:

```text
Did repository cloning succeed?
        ↓
Did environment creation succeed?
        ↓
Did dependency installation succeed?
        ↓
Did the web server start?
        ↓
Did app.py begin executing?
        ↓
At which exact line did it fail?
```

The lesson is:

> Fix the first genuine failure in the execution chain rather than changing several unrelated things at once.

# 68. V0 glossary

**Artifact** — A produced file or other output of a process.

**CLI** — Command-Line Interface; text-based interface invoked from a shell.

**Configuration** — Values that control behaviour without rewriting implementation logic.

**Current working directory** — Directory a running shell/process treats as the base for relative paths.

**Database driver** — Client library, such as psycopg, that lets application code communicate with a database server.

**DDL** — Data Definition Language; SQL for defining structures such as schemas, tables and indexes.

**Defect ledger** — V0 record of intentionally injected data-quality failures.

**Dependency** — Software package required by another software package/project.

**Direct dependency** — Package declared directly by Project MAX.

**Transitive dependency** — Package required by one of MAX's dependencies.

**Editable install** — Installation mode linking the Python environment to the working source tree so code edits are immediately reflected.

**Environment variable** — Process-level configuration supplied outside source code.

**Event time** — Time a business event actually occurred.

**Emission time** — Time the source system emitted/recorded an event for downstream use.

**Foreign key** — Database column whose value references a key in another table.

**Hash/checksum** — Deterministic fingerprint of bytes; V0 uses SHA-256.

**Immutable run** — Generated run treated as fixed evidence rather than silently overwritten.

**Index** — Database structure used to speed certain queries/lookups.

**Integration test** — Test that crosses component/system boundaries such as Python → PostgreSQL.

**JSONL** — JSON Lines; one JSON object per line.

**Manifest** — Metadata file describing a generated run and its artifacts.

**Module** — Importable Python file/module.

**Package** — Importable collection of Python modules.

**Primary key** — Unique identifier enforced by a relational table.

**Reproducibility** — Ability to regenerate the same controlled output under the same inputs/seed.

**Schema (database)** — Namespace/grouping of database objects inside a PostgreSQL database.

**Schema (data contract)** — Expected fields/types/structure of a record or event; context determines which meaning is intended.

**Seed** — Input initializing a pseudo-random generator so generated sequences can be reproduced.

**Serialization** — Conversion of in-memory objects into a storable/transmittable representation such as CSV or JSON.

**Session state** — Streamlit mechanism for retaining values across reruns within a user session.

**Source system** — Operational producer of data; V0 simulates several independent ones.

**Transaction (database)** — Group of database operations treated as a unit of work.

**Unit test** — Test focused on contained behaviour with minimal external dependencies.

**Upsert** — Insert a record when absent, update it when its key already exists.

**Virtual environment** — Isolated Python environment for project-specific interpreter/package resolution.

# 70. Handoff to V1

V0 leaves us with a coherent problem rather than a technology shopping list:

```text
We now have multiple operational source systems.
They emit different formats.
Some records are late.
Some truth arrives days later.
Some data is deliberately malformed.
Some information is relational.
Some is event-shaped.
Some is unstructured.
The local run directory is useful evidence but is not an analytical platform.
```

Therefore V1 can ask a natural engineering question:

> **How do we ingest these independent source artifacts into durable analytical storage while preserving the original source representation and recording what arrived?**

That is when landing/bronze storage, S3, ingestion metadata, quarantine, Parquet where appropriate, Glue/Athena and related platform concepts earn their place.

The concepts introduced in this V0 document should be treated as assumed knowledge in the V1 foundational-concepts document rather than explained again.
